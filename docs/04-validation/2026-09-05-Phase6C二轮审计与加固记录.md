# Phase 6C 二轮审计与加固记录

> 日期：2026-09-05  
> 范围：Phase 6B 修复后的二轮审计  
> 原则：验证修复是否真的改善 Agent 失败行为，同时检查是否引入新的工程风险

## 1. 二轮审计目标

Phase 6B 已经完成重复失败工具调用去重、配置候选资源提示和失败诊断复盘报告。

Phase 6C 不重复做全项目大审计，而是聚焦验证：

- 去重逻辑是否会被 JSON 参数顺序绕过；
- 配置候选路径是否真的从 ServiceProfile 进入首轮 LLM 上下文；
- 配置候选扫描是否会误扫或暴露构建产物；
- 文档和测试基线是否仍与真实工程一致。

## 2. 二轮发现

### 2.1 配置候选扫描需要遍历时剪枝

Phase 6B 初版 `LocalConfigRepository.list_candidate_paths()` 使用 `Path.rglob("*")` 收集候选文件，再过滤 `.git`、`target`、`build` 等目录。

这在小型 Java Lab 中没有问题，但如果 `config_workspace_path` 指向真实项目根目录，`rglob("*")` 仍会进入 `target`、`build` 等大目录，只是在文件命中后再过滤。风险是：

- 配置候选准备变慢；
- 大型构建目录可能拖慢一次诊断启动；
- 后续如果构建产物里有大量配置文件，扫描成本会被放大。

修复方式：

- 改为显式遍历目录；
- 遍历目录时直接跳过 `.git`、`.idea`、`target`、`build`、`.gradle`、`__pycache__`；
- 文件过滤只基于授权根目录内部的相对路径，避免因为父目录名称碰巧叫 `build` 而误伤。

## 3. 已补充测试

新增或确认的关键测试：

- 重复失败工具调用不会再次执行 Adapter；
- JSON 参数字段顺序变化时，重复失败签名仍然一致；
- 配置候选路径优先列出常见 `application.yml`；
- `target` 目录内配置不会进入候选；
- 授权根目录名碰巧叫 `build` 时，不会误伤根目录下真实配置；
- 服务绑定 config workspace 后，候选路径能进入首次 LLM 用户消息。

## 5. 是否需要真实模型复验

建议：需要，但不要自动批量复验。

适合复验的唯一案例是：

- Java Lab `timeout`;
- 使用修正后的 `InventoryClient.loadInventory` 日志定位关键词；
- 单次调用 DeepSeek；
- 不自动重试；
- 观察点不是单纯是否 pass，而是工具轨迹是否减少无效配置路径探测。

如果真实模型仍失败，优先判断：

- 是否仍有重复无效 `config__read`；
- 是否优先读取了候选 `src/main/resources/application.yml`；
- 是否在 Evidence 已足够时仍无法收敛；
- 是否需要把“已读到关键配置后应 finalization”的规则前移。

## 6. 下一步建议

如果 Phase 6C 继续推进，建议只做两件事：

1. 低频真实模型单案例复验 Inventory timeout；
2. 如果复验仍然无效，再考虑把 `ConclusionGuard` 或“成功读取关键配置后进入 finalization”抽出来。

不建议现在启动 Phase 5，也不建议大拆 `ToolLoopRunner`。当前更有价值的是把真实模型失败行为压实、讲清楚。
