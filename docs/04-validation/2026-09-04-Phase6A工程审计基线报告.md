> 审计日期：2026-09-04  
> 审计范围：Application Diagnosis Platform 当前 `main` 分支

## 1. 审计结论

当前项目已经不再是简单的 Agent Demo，而是一个具备工程边界意识的本地单机诊断 Agent 参考实现。

它的强项不是“模型回答问题”，而是围绕模型回答建立了确定性约束：

- 用户输入入库前脱敏；
- 工具调用受 Strategy、Registry、权限、预算和 schema 共同约束；
- 工具输出转换为 Evidence 后才允许被模型引用；
- 模型结论必须通过 Citation Policy 校验；
- 人工确认不覆盖模型原始结论，而是追加 Confirmation；
- Trace、Report、Evaluation、CI 和 Phase 验收文档已经形成闭环。

但是，如果把它按企业生产系统审计，仍然存在明显边界：

- 当前没有认证、授权和多租户隔离；
- Agent Runtime 职责开始集中，后续扩展规划、记忆、跨服务诊断时会遇到维护压力；
- 真实模型评测样本仍然偏小，不足以证明统计意义上的诊断准确率；
- 主动发现已有本地和企业 Adapter 骨架，但还不是长期运行的生产 Worker；
- 文档体系很丰富，但已有少量事实滞后和阶段表述残留。

因此，Phase 6 不应该继续堆功能，而应该进入“可信度加固”阶段：先修影响可解释性、可维护性和面试可信度的问题，再决定是否进入 Phase 5 跨服务诊断。

## 3. 架构一致性审计

### 3.1 当前做得好的地方

核心六边形边界仍然成立：

- `domain` 保存 Diagnosis、Evidence、Incident、Knowledge、Plan 等领域对象；
- `ports` 定义 LLM、Repository、Redaction、LogReader、CodeRepository、Notification、Broker 等接口；
- `adapters` 承接 SQLite、Local File、GitHub、GitLab、RabbitMQ、Redis、SMTP、Webhook 等外部实现；
- `application` 负责用例编排；
- `agent/runtime` 负责有界模型循环；
- `api/routes` 基本保持薄路由。

关键边界在代码里仍然清楚：

- `DiagnosisApplicationService.run()` 负责把 Diagnosis 推进到 `INVESTIGATING`，选择 Strategy，然后调用 Runner；
- `ToolLoopRunner.run()` 不直接修改 Diagnosis 状态，只返回 `ToolLoopResult`；
- `DiagnosisApplicationService._apply_result()` 是 Agent 结果进入状态机的收口；
- `EvidenceCitationPolicy.validate()` 是模型结论可采信性的确定性校验点。

这意味着项目主线没有偏离最初“确定性工程骨架包裹概率性模型核心”的设计。

- LLM 消息构造；
- 工具定义暴露；

- 现有测试全通过；
- 至少补一个“工具重复失败不会无限消耗”的单元测试；

## 4. Agent 行为质量审计

### 4.1 当前优势

项目已经具备一般 Agent Demo 少见的行为约束：

- Strategy 决定工具白名单；
- Registry 校验工具是否注册、启用、被 Strategy 允许、支持当前 ProblemType、具备权限；
- Pydantic 校验 LLM 输出的工具参数；
- 工具超时和总预算同时存在；
- `finalization_mode` 后不再暴露工具定义；
- Citation Policy 阻止模型伪造 Evidence ID；
- `confirmed` 只能由人工确认产生。

这条链路是项目面试时最值得讲深的部分。

### 4.2 主要不足

#### P1-AGENT-001：真实模型在复杂案例上仍然容易低效探索

证据：

- `docs/04-validation/2026-09-01-真实模型v1基线评测.md`
- `docs/04-validation/2026-09-01-真实模型v2单变量复验.md`
- `docs/04-validation/2026-09-01-真实模型迭代评测终版.md`

现象：

真实模型在 NPE 案例上可以完成日志与源码联合诊断，但在超时、连接拒绝、连接池耗尽等案例上出现过：

- LLM 超时；
- 达到最大轮次；
- 重复尝试不存在或不相关配置路径；
- 已读到关键配置后仍未及时收敛。

判断：

这不是“模型不可用”，而是当前工具体系给模型的搜索空间仍然偏自由。模型知道可以读配置，却不知道哪些配置路径是候选的、哪些失败路径不该重复尝试。

建议：

优先补“候选资源显式化”和“失败工具调用去重”：

- 服务目录暴露 `known_config_paths`；
- Config 工具或资源上下文提供候选文件列表；
- ToolLoopRunner 在同一 AgentRun 内记录失败工具签名，重复失败时直接返回去重提示；
- Strategy prompt 告诉模型优先使用候选路径。

验收要求：

- 不增加真实模型自动测试；
- 离线 Fake LLM 测试覆盖重复失败去重；
- 至少一次真实模型复验只允许单案例、单次调用；
- Trace 能看出模型减少了无效路径探测。

#### P1-AGENT-002：Plan 当前偏解释性，还没有真正参与调度

位置：

- `src/app_diagnosis/agent/runtime/tool_loop.py:381`

现状：

当前 `DiagnosisPlan.create_rule_based()` 是规则版计划，主要用于 Trace 和报告解释，不驱动工具执行顺序。

判断：

这不是 bug。Phase 3 的定位本来就是“轻量 Plan 增强可解释性”。但如果项目后续要更有 Agent 味，Plan 需要逐渐承担两类职责：

- 约束探索范围；
- 帮助失败后调整步骤。

建议：

Phase 6 暂不做完整 Plan-then-Execute，只增加“计划建议”和“工具去重”即可。真正的 Plan-then-Execute 可以作为 Phase 7 或 Phase 5 之后的增强。

## 5. 安全边界审计

### 5.1 当前优势

代码和日志读取边界比较明确：

- `LocalCodeRepository` 只读配置 workspace；
- `LocalLogFileReader` 只读配置 log root；
- `LocalConfigRepository` 只读配置 config root；
- 代码文件有扩展名、目录、大小和行数限制；
- 日志文件限制 `.log/.txt`、tail 大小、事件边界和最大摘录行数；
- Config 和 Log 工具在返回模型前会脱敏；
- `.env`、数据库和 demo 输出被 `.gitignore` 排除。

### 5.2 主要不足

#### P1-SEC-001：API 层没有认证授权，不能按企业接口暴露

位置：

- `src/app_diagnosis/api/app.py`
- `src/app_diagnosis/api/routes/*.py`

现状：

当前 API 面向本地单用户和演示环境，没有登录、RBAC、服务级权限、操作者身份注入。很多接口里 `actor` 固定为 `local-api-user`。

判断：

这符合个人学习项目定位，但不能包装成“企业生产平台已具备权限治理”。简历和面试中应该明确讲：

> 本项目目前重点验证诊断闭环、证据可信、受限工具和评测体系；企业认证、RBAC 和多租户隔离属于生产化演进项。

建议：

短期只写入 Phase 6 风险清单，不立即开发复杂鉴权。若为了面试增强可信度，可以加一个轻量 `X-Actor` 请求头审计，不做登录系统。

#### P2-SEC-002：评测结果目录已纳入 Git，需要制定公开样本规则

位置：

- `evals/results/real-model-v1/*`
- `evals/results/real-model-v2/*`
- `evals/results/real-model-v2-timeout-corrected/*`

现状：

这些结果当前来自 Java Lab 可控样本，纳入 Git 有助于展示真实模型评测。但如果后续接入真实公司日志，继续提交 `evals/results` 会有敏感数据风险。

建议：

新增一条规则：

- `evals/results/public-*` 可提交；
- `evals/results/local-*`、`evals/results/private-*` 必须忽略；
- 真实公司日志只能保存脱敏摘要和评分，不保存原文。

## 11. Phase 6B 建议实施顺序

建议只选 3 个最有价值的问题先修，不做功能堆砌：

1. **失败工具调用去重与候选资源提示**
   - 目标：减少真实模型重复探测不存在路径；
   - 验收：离线测试证明同一 AgentRun 下重复失败工具调用会被明确提示并减少无效执行；
   - 价值：直接回应真实模型评测暴露的问题。

2. **失败诊断复盘报告**
   - 目标：把一次失败诊断从多份 JSON/Trace 中提炼为一份可读报告；
   - 验收：对 v2 timeout corrected 案例生成复盘，明确“读到关键配置但未收敛”的原因；
   - 价值：提升可观测性和面试展示效果。

3. **文档可信度小修**
   - 目标：更新测试数量、标注阶段快照、补充公开评测样本规则；
   - 验收：README、docs/README 和核心手册无明显事实滞后；
   - 价值：成本低，但明显提升项目专业感。

暂不建议立即做：

- 完整 RBAC；
- 多租户；
- 独立 Worker；
- 真正 Plan-then-Execute；
- Phase 5 跨服务拓扑；
- 大规模真实模型批量评测。

这些不是不重要，而是当前投入产出比不如先修 Agent 可信度和复盘能力。

## 12. 总体判断

如果我是面试官，这个项目会吸引我，但我会追问：

- 为什么需要 Evidence，而不是直接相信模型？
- ToolLoopRunner 如何防止模型乱调工具？
- 为什么 confirmed 不能由模型给出？
- 真实模型评测失败时，你怎么判断是模型问题、prompt 问题、工具问题还是预算问题？
- 当前项目距离企业落地差什么？
- 为什么 Phase 5 暂缓？

当前工程已经有能力回答这些问题。Phase 6 的价值，是把回答从“我觉得”升级成“我审计过、测过、记录过、修过”。
