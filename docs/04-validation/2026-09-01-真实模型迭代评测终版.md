# 真实模型迭代评测终版

> [返回文档导航](../README.md)

## 1. 最终结论

真实模型迭代没有产生“完整通过率提升”，但成功把一个笼统的超时问题拆成三个可行动的工程边界：单次 LLM 超时、Agent 总时间预算、无效配置路径探测。

本轮到此停止真实调用。继续提高超时只会增加延迟和 Token，无法解决工具循环不收敛。

## 2. 版本演进

| 版本 | 唯一变化 | 有效结果 |
| --- | --- | --- |
| v1 | 30 秒 LLM 超时 | NPE 通过；连接拒绝、Inventory timeout、连接池耗尽均 `LLMTimeoutError` |
| v2 | LLM 超时提高到 60 秒 | 连接池生成正确根因；连接拒绝耗尽 120 秒总预算；原 timeout 样本受日志定位污染 |
| v2 corrected | 修正 timeout 唯一日志定位键，其他保持 v2 | 输入正确，但 6 轮、8 次工具调用后 `max_rounds_reached` |

## 4. 失败模式归因

模型已获得正确 Inventory 日志和 `application.yml`，但仍重复尝试 `application.properties`、根目录 `application.yml`、`README.md` 等路径，最终耗尽轮次。这不是 Evidence 丢失，也不是日志边界问题，而是工具选择缺少“已知候选路径”和“相同失败路径不得重复”的确定性约束。

连接拒绝案例也出现同类配置路径探测，因此该模式已经重复出现，具备后续优化价值。优先方案应放在 Tool Registry 或运行上下文：向模型暴露受限工作区内允许读取的配置候选，而不是继续扩大超时或仅靠 Prompt 猜路径。

## 5. 为什么停止 v3

- v2 已证明 60 秒能够避免部分单次请求超时；
- 总预算和轮次现在成为新的确定性闸门；
- 未实现配置候选约束前继续调用，只会重复已知失败；
- 本项目目标是以评测驱动改造，而不是通过反复采样挑选一次幸运结果。

## 6. 后续触发条件

只有完成以下离线能力后，才值得启动 v3：

1. `config__read` 向 Agent 提供允许读取的候选配置路径；
2. 同一运行中对相同失败路径去重；
3. 新增确定性测试证明失败工具调用数量下降；
4. v3 仍限制为少量案例、每例一次、零自动重试。

## 7. 面试表达

可以如实表述：首轮 4 条真实案例中 NPE 通过，三条因 30 秒模型超时失败；将超时提高到 60 秒后，连接池案例能够形成正确根因，但连接拒绝触发总预算、Inventory timeout 因重复配置探测耗尽轮次。项目通过评测发现，下一步优化点不是继续加 Token，而是缩小工具搜索空间并对失败调用去重。
