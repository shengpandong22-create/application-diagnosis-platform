# 真实模型 v2 单变量复验

> [返回文档导航](../README.md)

## 1. 实验问题

v1 中连接拒绝、超时和连接池耗尽三个案例均以 `LLMTimeoutError` 结束。v2 只把 `llm_timeout_seconds` 从 30 秒提高到 60 秒，模型、Prompt、Strategy、工具 Schema、Agent 总时间预算和案例输入均保持不变。三条案例各执行一次，不自动重试。

## 2. 原始结果

| 案例 | v1 | v2 | v2 耗时 | 判断 |
| --- | --- | --- | ---: | --- |
| 连接拒绝 | `LLMTimeoutError` | `time_budget_exhausted` | 120,189 ms | 单次模型超时消失，但 120 秒 Agent 总预算耗尽，仍无结论 |
| timeout | `LLMTimeoutError` | `completed` | 48,211 ms | 输入误选为后续连接池事件，本条评测无效 |
| 连接池耗尽 | `LLMTimeoutError` | `completed` | 77,983 ms | 正确定位 size=1 下二次借用导致等待超时，但未成功读取配置，完整验收失败 |

原始三条 Suite 为 0/3 完整通过，结构化输出率、终止原因匹配率、Root Cause Top1 和引用有效率均为 66.67%。这些比例包含受污染的 timeout 案例，只作为原始产物保留，不能作为正式效果结论。

## 3. 有效样本对比

排除 timeout 污染样本后，v2 有效样本为连接拒绝和连接池耗尽两条：

| 指标 | v1 同案例 | v2 同案例 |
| --- | ---: | ---: |
| 完整通过 | 0/2 | 0/2 |
| 生成结构化结论 | 0/2 | 1/2 |
| Root Cause Top1 命中 | 0/2 | 1/2 |
| 终止原因匹配 | 0/2 | 1/2 |
| 必需 Evidence 完整 | 1/2 | 1/2 |

提高单次模型超时带来了局部改善，但没有提高完整通过数，因此不能声称 v2 已解决问题。

## 4. 新发现的两个边界

### 4.1 预算嵌套

连接拒绝案例说明单次 LLM 超时和 Agent 总时间预算必须协调。模型超时提高到 60 秒后，Runner 能继续更多轮次，但最终触发 120 秒总预算。继续只提高 LLM 超时会让失败更慢，并增加 Token 消耗。

### 4.2 同类异常输入污染

timeout 案例原先使用通用关键词 `TimeoutException`。日志中更晚出现连接池 `TimeoutException` 后，`read_latest` 合法地返回最近一次匹配事件，却不是目标 Inventory 故障。

正式定义已改用唯一栈帧 `InventoryClient.loadInventory`，并新增回归测试，验证后续连接池异常不会混入 Inventory timeout 摘录。该修复属于评测工具正确性，不计为模型能力提升。

## 5. D5 决策

本轮不同时修改总时间预算、Prompt 和配置工具行为。下一步应先对修正定位键后的 timeout 案例做一次替代复验，补齐无污染样本；该调用不在本轮“三条各一次”的授权范围内，需要单独授权。

若替代复验能完成结论，再决定是否值得开展第三轮：

- 连接拒绝可研究压缩无效配置探测，减少轮次和 Token；
- 连接池案例可研究让 Strategy 提供项目内已知配置候选路径；
- Agent 总预算只有在工具路径收敛后仍不足时再调整。
