# ADR-0005：将应用时间作为可注入依赖

> [返回文档导航](../README.md)

## 状态

Accepted

## 背景

诊断、Evidence 和运营统计都依赖时间。此前部分对象直接读取系统当前时间，测试却使用固定日期构造发现事件，导致同一业务链路中的事件日期与诊断日期不一致，日报统计在跨天后出现不稳定失败。这不是统计公式错误，而是应用内部存在多个不可控的时间来源。

## 决策

诊断主链路使用可注入的 `clock: Callable[[], datetime]`，默认实现仍返回 UTC 当前时间。容器负责创建并向 `DiagnosisApplicationService`、`ToolLoopRunner` 和 `SqlAlchemyEvidenceStore` 传递同一时钟；领域对象继续只接收显式的 `now`，不依赖框架或基础设施。

本次只治理“创建诊断及其 Evidence”的时间一致性，不把时钟扩散为全局单例，也不在 D1 一次性改造主动发现、Incident 和所有审计记录。后续模块若需要跨时间边界的确定性测试，应从组合根显式接收同一时钟。

## 验证要求

- 默认生产行为仍使用 UTC 当前时间；
- 测试可注入固定 UTC 时间，并验证不同历史日期下日报统计一致；
- `DiagnosisCase.created_at` 与同一次运行产生的 Evidence 时间来自同一时钟；
- 不通过 monkeypatch 修改 Python 全局时间；
- 全量测试和 Ruff 检查通过。

## 取舍

- 显式传递时钟增加少量构造参数，但消除了日期相关测试对执行当天的依赖；
- 采用函数协议而非引入第三方 Clock 框架，保持当前单机项目的实现轻量；
- 分阶段治理避免扩大 D1 范围，但主动发现链路目前仍有独立时间来源，若 Phase 5 需要跨服务时序推断，应继续统一。
