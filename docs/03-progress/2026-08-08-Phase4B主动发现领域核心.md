# 2026-08-08：Phase 4B 主动发现领域核心

## 1. 阶段目标

Phase 4B 把平台从“只能接收人工发起的诊断”推进到具备主动发现所需的确定性领域核心，但暂不监听日志、不自动创建 Diagnosis，也不调用 LLM。

本阶段建立的链路为：

```text
结构化日志输入
  → 入库前脱敏
  → LogEvent
  → 版本化 ErrorFingerprint
  → 固定时间窗口
  → Incident 原子聚合
```

文件监听、Replay Source 和自动诊断触发属于 Phase 4C。

## 2. 核心设计

### 2.1 指纹稳定性

`v1` 指纹使用：算法版本、service_id、environment、规范化异常类型和前五个业务栈帧。栈帧只保留类名与方法名，因此源码行号变化不会改变指纹。服务或环境不同则默认产生不同指纹，避免跨服务误聚合。

### 2.2 窗口与 novelty

当前使用 15 分钟固定时间桶：

- 同一聚合键首次出现：创建 Incident，`is_novel=true`；
- 同一窗口再次出现：原子增加 `occurrence_count`；
- 超过窗口：创建新的 Incident；
- 乱序事件：`first_seen_at` 取最小值，`last_seen_at` 取最大值。

### 2.3 并发与幂等

数据库对 `aggregation_key` 建立唯一索引。多个协程同时插入时，仅一个成功创建，其余通过原子 UPDATE 聚合，不依赖进程内锁。

`DeduplicationStore` 提供内存和 SQLite 语义。带 `source_event_id` 的相同事件重放不会重复增加次数；去重有效期基于接收时间，而不是历史事件时间。

### 2.4 安全边界

API 收到的 message 被视为不可信内容，先经过 `LocalRuleRedactor`，再构造 LogEvent 和 Incident。Incident 中只保存脱敏后的安全样例，不保存原始密钥。

## 3. 新增能力

- `LogEvent`、`StackFrame`、`ErrorFingerprint`、`Incident` 领域模型；
- `IncidentRepository`、`DeduplicationStore` Ports；
- SQLAlchemy Incident Repository；
- 内存与 SQLite 去重实现；
- Alembic `0011`；
- `POST /api/v1/incidents/events`；
- `GET /api/v1/incidents`；
- `GET /api/v1/incidents/{id}`；
- Phase 4B 一键验收脚本。

## 4. 明确未实现

- 不监听本地日志文件；
- 不连接 MQ、Redis 或日志平台；
- 不自动创建或运行 Diagnosis；
- 不调用真实模型；
- 不生成 Evidence。

这些边界保证 4B 只验证确定性的主动发现基础，不把 4C 的外部输入和 Agent 副作用混入领域测试。
