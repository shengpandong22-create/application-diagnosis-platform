## 开发经验沉淀

### 1. 可观测性不能超出已持久化事实

现有 AgentRun 只有聚合轮次和 Token，没有每轮 LLM 时间戳。Trace v1 因此只构造 run/tool/finish 事件，没有为了视觉效果伪造 Round 时间线。

### 2. ToolRun 与 Evidence 的顺序决定可追踪性

原流程先记录 ToolRun，再持久化 Evidence，ToolRun 无法知道正式 Evidence ID。Phase 2 调整为先落库 Evidence，再把 ID 写入 ToolRun，最后回传模型，从而形成稳定关联。

### 3. “只读”仍然需要威胁建模

配置读取可能泄漏密码，日志读取可能跨目录，健康检查可能形成 SSRF。因此权限级别只是一个维度，还需要目录、目标、Schema、超时、输出和脱敏的组合边界。

### 4. 组合验收能发现单脚本发现不了的问题

Phase 2 演示单独运行成功，但第一次放入一键验收时，外层 `APP_DATABASE_URL` 干扰了演示临时库迁移。修复后演示会在迁移期间隔离外层变量。这说明验收脚本本身也属于需要测试的工程代码。

## 当前边界

- Trace 尚无逐轮 Prompt/Response 持久化；
- Router 是规则分类，不是模型路由；
- 健康检查仅允许本机预配置 HTTP 目标；
- 不执行 Shell、配置修改、进程重启或自动修复；
- 未实现 Plan-then-Execute；
- 未实现人工确认后的 KnowledgeCandidate 自动提取。

## 后续候选方向

下一步不应立即同时实现 Planner、自动修复和长期记忆。建议先使用 Phase 2 工具增加一个需要“日志 + 配置 + 健康检查”才能判断的 Java Lab 复杂案例，通过真实模型低频验收观察 ReAct 是否出现明确瓶颈，再决定 Phase 3 是规划能力还是经验沉淀。
