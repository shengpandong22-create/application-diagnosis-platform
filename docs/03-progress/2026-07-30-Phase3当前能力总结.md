# 2026-07-30：Phase 3 当前能力总结

## 一、为什么要做 Phase 3

Phase 0～2 已经把诊断闭环的底座搭起来了：

- Phase 0A：可运行的最小 Agent Loop；
- Phase 0B：Evidence、知识库、人工确认和审计；
- Phase 0C：报告、评测和极简展示；
- Phase 1：真实日志与受限源码联合诊断；
- Phase 2：Trace、多 Strategy、配置/日志/健康检查工具。

但走到这里后，项目还存在一个问题：系统已经能诊断“一个请求”，但还没有把诊断对象沉淀成“一个服务”。

真实 ITOps 场景里，故障通常不是孤立文本，而是发生在某个服务上。这个服务有源码目录、日志目录、配置位置、健康检查地址，也会有后续负责人、依赖关系和历史诊断记录。

所以 Phase 3 的目标不是继续堆模型能力，而是把诊断闭环讲深：

> 让 Agent 的每一次诊断都有可解释计划、可追踪执行轨迹，并逐步绑定到真实服务对象。

## 二、Phase 3 分阶段完成内容

### 3A：代码可读性与架构学习材料

3A 的重点不是功能，而是让项目更像一个可交接的工程。

完成内容：

- 为关键主流程代码补充工程化中文注释；
- 整理源码学习路线图；
- 固化架构图风格规范；
- 强调“注释解释边界和意图，不逐行翻译代码”。

这一步解决的问题是：后续你作为开发者回头学习源码时，不只是知道代码写了什么，还知道为什么这么分层、为什么保持某些边界。

### 3B：轻量诊断计划

3B 引入了规则生成的 `DiagnosisPlan`。

它不是复杂的 LLM Planner，而是一个确定性、可持久化、可展示的计划对象：

- 和 `AgentRun` 关联；
- 根据 Strategy 与允许工具生成步骤；
- 在 Trace 和 Report 中展示；
- 帮助解释“Agent 接下来准备如何调查”。

这一步解决的问题是：用户不只看到最终答案，还能看到诊断前的调查意图。

### 3C-1：最小服务目录

3C-1 引入 `ServiceProfile`。

服务目录保存：

- 服务名称；
- 环境；
- 描述；
- 源码目录；
- 日志目录；
- 配置目录；
- 健康检查目标；
- 标签。

同时 `DiagnosisCase` 增加 `service_id`，支持通过服务创建诊断。

这一步解决的问题是：诊断对象从“一段用户输入”升级为“某个明确服务的一次故障”。

### 3C-2：服务目录驱动工具上下文

3C-2 是 Phase 3 的关键闭环。

以前工具主要由全局 `.env` 配置启用。现在，绑定服务的诊断可以从 `ServiceProfile` 获得本次运行的受限工具上下文：

- `code_workspace_path` → `code__search` / `code__read`
- `log_directory` → `log__search`
- `config_workspace_path` → `config__read`
- `health_targets` → `health__check`

核心新增对象：

- `ToolResourceContext`：表示单次 AgentRun 可使用的服务级资源；
- `ToolResourceResolver`：根据 `DiagnosisCase.service_id` 解析服务级 Adapter；
- 扩展 `ToolExecutionContext`：把服务级 Adapter 传入工具执行层；
- 扩展 Strategy：根据本次可用资源动态暴露工具白名单。

这一步解决的问题是：LLM 不能任意选择本机工具，只能看到当前服务显式授权范围内的工具。

### 3C-3：服务驱动演示链路

新增离线演示脚本：

```powershell
uv run python scripts/demo-phase3-service.py
```

该脚本会自动完成：

1. 创建临时数据库；
2. 创建临时 Java 服务目录；
3. 注册 `ServiceProfile`；
4. 通过服务创建诊断；
5. Fake LLM 调用 `code__search` 和 `code__read`；
6. 生成 `code_excerpt` Evidence；
7. 输出 Trace 和 Report。

这一步让 Phase 3 具备一条完整展示链路：

> 服务目录 → 诊断 → 工具上下文 → 工具调用 → Evidence → Trace → Report

## 三、当前可演示能力

现在项目可以演示三条层级递进链路。

### 1. 最小诊断闭环

```text
创建诊断 → Agent Loop → Knowledge Tool → Evidence → 人工确认 → Report
```

适合解释 Phase 0 的基本闭环。

### 2. 日志与源码联合诊断

```text
Java Lab 故障日志 → Log Evidence → code__search/read → Code Evidence → 引用校验 → Report
```

适合解释 Phase 1 的真实故障定位能力。

### 3. 服务目录驱动诊断

```text
ServiceProfile → Diagnosis.service_id → ToolResourceContext
→ Strategy 动态工具白名单 → ToolExecutionContext
→ 受限 Adapter → Evidence / Trace / Report
```

适合解释 Phase 3 的服务化诊断对象建模。

## 四、这部分面试应该怎么讲

可以这样表达：

> 我没有一开始就做复杂的多 Agent 或自动化修复，而是先从诊断闭环的可信链路入手。第一步让 Agent 能运行，第二步让结论必须基于 Evidence，第三步让日志和源码形成联合诊断，第四步补充 Trace 和策略路由，最后把诊断对象抽象成服务目录。这样后续无论是做服务依赖、历史诊断记忆，还是自动化处置，都有明确的服务上下文和安全边界。

如果面试官问“服务目录有什么价值”，可以回答：

> 它把工具授权从全局配置变成了单次诊断上下文。Agent 不是拥有整台机器的读取能力，而是只拥有当前服务显式配置的源码、日志、配置和健康检查目标。这样既更贴近 ITOps 场景，也更容易做权限控制和审计。

如果面试官问“为什么不用 LLM 直接决定读哪里”，可以回答：

> LLM 可以提出工具调用意图，但不能决定权限边界。权限边界由 ServiceProfile、ToolResourceResolver、Strategy 白名单、Registry 和 Adapter 路径校验共同控制。这样可以把概率性推理限制在确定性工程边界内。

## 六、当前边界

当前服务目录仍是最小实现：

- 没有服务依赖图；
- 没有服务负责人；
- 没有服务级历史诊断聚合；
- 没有服务自动发现；
- 没有自动生成修复 PR；
- 没有真正的多步 LLM Planner；
- 没有把诊断结论自动沉淀成候选知识。

这些边界是刻意保留的。当前阶段优先保证诊断主链路清晰、安全、可展示。

## 七、下一步建议

下一阶段建议进入 Phase 4A：服务目录增强。

优先级建议：

1. 服务详情页/查询接口增强：按服务查看历史诊断；
2. 服务默认诊断入口：按服务聚合 Evidence、Trace、Report；
3. 服务依赖关系：定义上游/下游服务关系；
4. 服务健康概览：展示最近健康检查和最近诊断状态；
5. 再考虑诊断记忆：从 confirmed 诊断中生成候选 KnowledgeEntry。

我的建议是先不要急着做“自动学习”。先把服务目录这个诊断对象稳定下来，再做记忆沉淀，会更像一个真实 ITOps 平台，而不是一个功能拼盘。
