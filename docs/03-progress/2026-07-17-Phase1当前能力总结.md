> 本文记录 Phase 1 的实现、验收和开发经验。架构演进的完整解释请阅读[Phase 1 扩展架构与深度学习总结](../01-architecture/phase1-extension.md)；一次调用的顺序请阅读[Phase 1 端到端链路图](../01-architecture/phase1-log-code-flow.md)。

## 阶段定位

Phase 1 的目标，是把 Phase 0A/0B/0C 已经具备的“证据驱动诊断闭环”，向真实开发场景推进一步：

> 使用 Python Agent 分析 Java Lab 产生的真实异常日志，并在受限范围内检索、读取 Java 源码，最终形成同时引用日志 Evidence 与源码 Evidence 的结构化诊断结论。

这不是复杂代码 RAG，也不是扫描本机任意工程。当前路线刻意保持小而可控：先构造一个可重复的 Java 故障实验室，再让诊断平台具备受限源码搜索和读取能力。

## 已完成能力

### 1. 受限源码诊断工具

新增 `code__search` 与 `code__read` 两类工具：

- 只允许访问配置的 `code_workspace_path`；
- 搜索结果返回相对路径、行号和简短预览；
- 源码读取结果会生成 `code_excerpt` Evidence；
- 工具调用受 Strategy 白名单、Registry 参数校验、工具预算和超时约束；
- 读取源码后，Agent 进入无工具最终结论阶段，避免无休止调查。

这一层的重点不是“让模型想读哪里就读哪里”，而是让模型在受控边界内获取足够源码证据。

### 2. 真实 Java Lab 故障实验室

独立 Java 项目 `diagnosis-java-lab` 已提供三个可重复故障接口：

| 故障 | 接口 | 关键日志 | 关键源码 |
|---|---|---|---|
| NPE | `/lab/orders/npe` | `NullPointerException` | `OrderService.java` |
| 连接拒绝 | `/lab/payments/connection-refused` | `ConnectException` | `PaymentClient.java` |
| 超时 | `/lab/inventory/timeout` | `TimeoutException` | `InventoryClient.java` |

Java Lab 将日志写入固定文件 `logs/diagnosis-java-lab.log`，便于 Python 诊断平台做可重复验收。

### 3. 真实日志读取与事件边界

新增受限 `LocalLogFileReader`：

- 只能读取配置日志目录内的文件；
- 根据故障关键词提取最近一次相关异常；
- 按日志事件起始行与堆栈连续行截取单个异常事件；
- 读取结果在入库前复用现有脱敏流程；
- 日志内容以 `log_excerpt` Evidence 进入诊断闭环。

这个改动解决了早期固定窗口截取可能混入后续异常的问题，减少无关 Token 和跨事件干扰。

### 4. Evidence 引用收敛

真实模型在复杂案例下曾出现一种稳定失败：日志和源码都读到了，但最终 JSON 结论没有正确引用已有 Evidence ID。

已完成的收敛修复：

- Agent 首轮向模型提供当前 Diagnosis 已有 Evidence 目录；
- 最终结论阶段再次提供当前权威 Evidence 目录；
- 结构化输出纠错与 Evidence 引用纠错拆分预算；
- Evidence 引用错误最多允许两次专门纠错；
- 引用纠错明确要求 source-based root cause 同时引用运行日志和相关源码 Evidence。

这个点很重要：系统没有绕过模型伪造结论，而是强化“模型必须基于可追踪证据完成结论”的约束。

### 5. 低频真实模型验收

DeepSeek `deepseek-v4-pro` 已完成三类 Java Lab 故障真实模型验收：

| Case | 结果 | 说明 |
|---|---|---|
| `npe` | 通过 | 定位 `OrderDraft(null)` 到 `customer.trim()` 的空值解引用 |
| `connection-refused` | 通过 | 定位 `PaymentClient` 连接本地未监听端口导致拒绝 |
| `timeout` | 通过 | 定位 `InventoryClient` 中 `Future.get(timeoutMs, TimeUnit.MILLISECONDS)` 超时 |

真实模型调用保持低频：失败后先分析报告和运行摘要，再修复离线逻辑，最后复验。

## 当前架构价值

Phase 1 已经让项目从“日志 + 知识库候选诊断”升级为“日志 + 源码联合诊断”。

当前主流程是：

1. Java Lab 触发真实异常并写入日志；
2. Python 平台读取最近一次相关异常日志；
3. 日志脱敏后形成 `log_excerpt` Evidence；
4. Agent 基于 Evidence 调用受限源码工具；
5. `code__search` 找到候选源码；
6. `code__read` 读取关键片段并生成 `code_excerpt` Evidence；
7. Agent 生成结构化结论；
8. Citation Policy 校验 Evidence 归属和引用规则；
9. 生成 Markdown 报告，可继续人工确认、驳回或补充调查。

这条链路对展示很有价值，因为它不是单纯让模型“猜原因”，而是要求模型在受限工具和可追踪证据下完成诊断。

## 仍然保留的边界

当前还不是生产级代码智能平台：

- 没有代码向量库；
- 没有跨仓库索引；
- 没有自动扫描本机任意工程；
- 没有 Worker、队列或异步后台任务；
- 没有长期模型质量统计；
- 没有前端化的故障实验台；
- 没有企业权限、审计检索和多用户隔离。

这些边界是有意保留的。当前阶段更重要的是证明核心闭环成立，并让每一步都有测试和验收记录。

## 开发经验沉淀

### 1. 真实模型失败不等于能力失败

`timeout` 案例前两次真实调用失败，但日志读取、源码搜索和源码读取都成功。真正的问题是最终结论引用 Evidence ID 失败。

因此排查真实模型问题时，要先看工具轨迹和 Evidence，再判断是检索失败、上下文不足、Schema 失败，还是引用策略失败。

### 2. 不要用重复调用掩盖工程问题

失败后如果立刻连续重试，可能偶然通过，但系统问题仍然存在。

这次采用的节奏是：

- 第 1 次失败：确认失败集中在 Evidence 引用；
- 离线修复：最终结论阶段补充 Evidence 目录；
- 第 2 次失败：发现单一纠错预算仍不够；
- 离线修复：拆分结构化纠错和引用纠错；
- 第 3 次复验：通过。

这个节奏比“刷模型直到成功”更适合长期工程化。

### 3. Agent 的关键不是能调用工具，而是能受控收敛

Phase 1 中最有价值的改动不是新增 `code__read` 本身，而是这些约束：

- 代码读取范围受限；
- 工具预算可预测；
- 读取源码后进入无工具结论阶段；
- 结论必须引用真实 Evidence；
- 引用违规可以被纠错，但不能无限纠错。

这些约束让 Agent 从 demo 更接近工程系统。
