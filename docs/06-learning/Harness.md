# 面试话术：Harness 理解与项目应用

> 对应项目：`src/app_diagnosis/agent/runtime/tool_loop.py` 的 `ToolLoopRunner`
> 面试问题：你如何理解 harness？你项目中如何使用 harness？这样做的好处是什么？

---

## 一、电梯 Pitch（30 秒）

> 我的诊断项目里，Agent 是"马"，业务是"车"，我写的 harness 是套在中间的马具——`ToolLoopRunner`。它不负责让模型更聪明，只负责让模型更**可信**：多轮循环、工具白名单、预算超时、证据引用校验，全在它这一层。核心就一句话：**模型负责"生成什么"，harness 负责"什么能做、做到什么程度、怎么收场"。** 有了这层，LLM 从"会接话"变成了"能上生产的组件"。

---

## 二、核心故事（2 分钟）

### 开场：一个不可控的模型

我们的 Agent 要诊断一个订单服务的 NPE。模型第一轮很聪明——它说"我看到了 `NullPointerException`，让我去读日志"。读到日志后它又说"堆栈指向 `OrderService.java:127`，让我读代码"。到这里都很好。

但问题来了：**如果我不给它套 harness，它随时会跑偏。** 它可能调一个根本不存在的工具、可能引用一段它自己编出来的日志、可能读完代码还停不下来一直查下去、可能输出一个格式乱七八糟的 JSON 让我解析崩溃。

### 中段：harness 怎么把它管住的

我写的 `ToolLoopRunner` 就干四件事：

1. 它说"读日志"，我**先校验**——`log__search` 在不在这个诊断的白名单里、参数合不合法，通过了才真正执行；
2. 它读完关键代码，我**主动关门**——把工具列表从下一轮请求里撤掉，逼它只能输出结论，不能再查；
3. 它输出的结论，我**校验引用**——它引用的每个 Evidence ID 必须真的属于这次诊断，编造的会被打回，给一两次改正机会，改不对就标 `INCONCLUSIVE`；
4. 整个过程有**硬预算**——最多 6 轮、8 次工具调用、120 秒，超了直接收场，绝不无限烧钱。

### 收尾：为什么这层重要

结果就是，同样一个模型，裸奔时它是 demo——演示很炫，一上线就翻车；套上 harness 后，它的每一步都有据可查（每一轮 prompt、每一次工具调用、每一次失败都落库成 `AgentRun`/`ToolRun`），结论有证据链支撑，成本有上限。

所以我一直说：**模型这两年变强得很快，但"怎么把模型可靠地接进生产"这道题，比模型本身更难，而这道题恰恰是 harness 要答的。** 这是我做这个项目最有价值的收获。

---

## 三、一句话版本（被突然打断时兜底）

> 我的项目里 harness 是 `ToolLoopRunner`，它解决"概率模型输出"和"确定性工程约束"之间的张力——模型提意图，系统校验后才执行，让 Agent 从 demo 变成能上生产的组件。

---

## 四、追问防御

| 可能的追问 | 应对 |
|-----------|------|
| "这不就是 agent loop 吗？" | 是，harness 和 agent loop 是同一个东西的不同叫法，harness 更强调"约束层"这层含义 |
| "为什么不用现成框架（LangChain/LangGraph）？" | 我们这块逻辑不复杂但约束很重（引用校验、预算、审计），自己写反而能精确控制边界；框架更适合快速搭原型，我们更看重可追溯和可测试 |
| "harness 和 strategy 什么关系？" | strategy 决定"用什么 prompt、允许哪些工具"，harness 负责"在这个约束下怎么跑"。strategy 是配置，harness 是执行引擎 |

---

## 五、核心理解备忘

harness 的职责边界（五件事）：驱动循环、管理上下文、调度工具、施加约束、收敛结果。

关键边界：**harness 不做业务决策**——它不知道"这个故障该怎么诊断"，它只知道"如何让模型在规则内跑完诊断这件事"。

一句话总结：**模型负责智能，harness 负责可信。**
