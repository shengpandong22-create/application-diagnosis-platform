# 第2课附录：8 步主调用链 · 代码逐步骤解读

对应教案 §2.2，"以一次 NPE 诊断为例，理解 HTTP 请求如何经过应用编排并收敛为领域状态"。

## 结构关系（先看这个）

教案中的 8 步不是 8 个平级函数，而是调用层级关系：

```
HTTP 层：
[1] 路由处理器 run_diagnosis()                    ← api/routes/diagnoses.py
↓ 调用
应用层：
[2] DiagnosisApplicationService.run()              ← application/diagnoses.py（主入口方法）
├─ [3] _start_investigation()            ← 状态门禁（run() 内部的第一个子步骤）
├─ [4] StrategyRouter.select()            ← 策略选择（run() 内部的第二个子步骤）
├─ [5] ToolResourceResolver               ← 资源解析（run() 内部的第三个子步骤）
├─ [6] ToolLoopRunner.run()               ← Agent 循环（run() 内部的第四个子步骤）
└─ [7] _apply_result()                    ← 结果收敛（run() 内部的第五个子步骤）
   └─ [8] Repository.save()             ← 持久化（_apply_result 内部的收尾操作）
```

为什么步骤 [2] 的代码片段包含了 [3]~[7]？因为 `run()` 就是大管家——它内部依次调用了后面所有子步骤。解读 [2] 时展示全貌是为了让你看到编排关系，解读 [3]~[8] 时再看每步的具体实现。

## [1] POST /api/v1/diagnoses/{id}/runs

源码位置：`api/routes/diagnoses.py` 第 62-75 行

```python
async def run_diagnosis(diagnosis_id: UUID, request: Request) -> RunResultResponse:
    result = await _service(request).run(
        diagnosis_id,
        actor="local-api-user",
        environment=settings.env,
        correlation_id=request.state.request_id,
        max_tool_output_bytes=settings.tool_output_max_bytes,
    )
    return RunResultResponse.from_result(result)
```

### 解读

- `_service(request)` → 从 FastAPI 的 `app.state` 取出 bootstrap 装配好的 `DiagnosisApplicationService`（第 30-32 行）。路由层自己不 new 任何对象，依赖完全由 bootstrap 注入。
- `actor="local-api-user"`：硬编码的调用者标识。如果将来有 OAuth/JWT 用户体系，这里会改成从 token 中提取。
- `request.state.request_id`：每个 HTTP 请求的唯一 ID，作为 `correlation_id` 贯穿整个诊断链路，用于审计追踪。
- 路由层没有做参数校验——校验在第 [2] 步的 `run()` 方法内部。
- **设计原则**：路由层刻意保持很薄（文件头注释："不承载 Agent Loop、Evidence 创建或状态机逻辑"）。

## [2] DiagnosisApplicationService.run(diagnosis_id)

源码位置：`application/diagnoses.py` 第 220-277 行

```python
async def run(self, diagnosis_id, *, actor, environment, correlation_id, max_tool_output_bytes):
    task = asyncio.current_task()
    # ① 并发保护
    async with self._active_lock:
        if diagnosis_id in self._active_tasks:
            raise DiagnosisRunConflict("diagnosis already has an active run")
        self._active_tasks[diagnosis_id] = task

    try:
        # ② 推进状态 → [3]
        diagnosis = await self._start_investigation(diagnosis_id, actor=actor, correlation_id=correlation_id)
        # ③ 选择策略 → [4]
        strategy = self._strategy_router.select(diagnosis) if self._strategy_router else self._strategy
        # ④ 解析资源 → [5]
        resources = await self._tool_resource_resolver(diagnosis) if self._tool_resource_resolver else ToolResourceContext()
        # ⑤ 调用 Runner → [6]
        result = await self._runner.run(diagnosis=diagnosis, strategy=strategy, context=..., budget=self._budget)
        # ⑥ 结果回写状态机 → [7]
        await self._apply_result(diagnosis_id, result)
        return result
    except asyncio.CancelledError:
        await asyncio.shield(self._mark_cancelled(diagnosis_id))
        raise
    finally:
        # ⑦ 释放并发锁
        async with self._active_lock:
            self._active_tasks.pop(diagnosis_id, None)
```

### 解读：四个关键设计点

#### 2.1 `_active_tasks` 字典（第 226-232 行）

单进程并发保护。`_active_lock` 是 `asyncio.Lock()`，保证对 `_active_tasks` 字典的读写是原子的。`_active_tasks` 是一个 `dict[UUID, asyncio.Task]`，在 `run()` 的 `finally` 块中一定会清理（第 276-277 行），即使抛异常。

#### 2.2 `CancelledError` 特殊处理（第 272-274 行）

当用户调 `cancel()` API 时，会调用 `task.cancel()` 向对应的 asyncio Task 发送取消信号。`run()` 捕获这个信号后用 `asyncio.shield()` 保护 `_mark_cancelled()` 不被继续取消——确保即使取消操作本身，状态也会正确写入 `CANCELLED`。

#### 2.3 `_active_lock` 和数据库乐观并发控制是两层

`_active_lock`（内存锁）只保护同一进程内的重复运行。数据库层用 `version` 做乐观并发检测；它不是会阻塞其他事务的“数据库锁”，而是在保存时拒绝基于旧版本的更新。两者处理不同时间窗口。

#### 2.4 一步一注释（第 247-248 行）

```python
# LLM 运行只拿到 Strategy、权限和预算；它不能直接修改 DiagnosisCase。
# 这条边界很关键，后续增加更多 Agent 能力时也不应绕过。
```

这是设计意图注释——防止后来者无意中打破权力边界。

## [3] DiagnosisCase: CREATED → INVESTIGATING

源码位置：`application/diagnoses.py` 第 309-343 行（`_start_investigation`）

```python
async def _start_investigation(self, diagnosis_id, *, actor, correlation_id) -> DiagnosisCase:
    async with self._sessions.begin() as session:
        diagnosis = await repository.get(diagnosis_id)
        # 状态门禁
        if diagnosis.status not in {DiagnosisStatus.CREATED, DiagnosisStatus.INVESTIGATING}:
            raise DiagnosisRunConflict(...)
        # 只在 CREATED 时推进状态
        if diagnosis.status is DiagnosisStatus.CREATED:
            expected_version = diagnosis.version       # ← 记住旧版本号
            diagnosis.start_investigation()            # ← version +1
            await repository.save(diagnosis, expected_version=expected_version)  # ← 乐观锁写入
        # 审计事件在状态推进之后记录（同事务）
        await audit_repo.add(AuditEvent.create(
            actor=actor,
            action="diagnosis.run_started",
            target_type="diagnosis",
            target_id=str(diagnosis.id),
            correlation_id=correlation_id,
        ))
        return diagnosis
```

### 解读：三个关键细节

#### 3.1 对 INVESTIGATING 状态的重入容忍（第 329 行）

`if diagnosis.status is DiagnosisStatus.CREATED`——只有 `CREATED` 才做转换。如果已经是 `INVESTIGATING`（重试场景），跳过状态转换但依然记录审计事件。这只说明状态门禁容忍已经处于 `INVESTIGATING` 的诊断重新进入；不能据此称整个 `run()` 幂等，因为后续仍会创建新的 `AgentRun` 并再次调用模型。真正的请求级幂等还需要显式幂等键或持久化运行声明。

#### 3.2 乐观锁用法（第 330-332 行）

```python
expected_version = diagnosis.version    # 先记"当前版本"
diagnosis.start_investigation()         # version 变了（+1）
await repository.save(diagnosis, expected_version=expected_version)  # 用旧版本号校验
```

`save()` 的 WHERE 条件是 `version == expected_version`。如果中间有人改过数据库，`rowcount=0` 抛 `ConcurrentDiagnosisUpdate`。

#### 3.3 审计事件集中化

本方法的 docstring 写明了意图（第 312-315 行）："这里是运行开始审计的集中位置，避免 API 层和 Runner 分散记录。" 这是一条架构纪律：审计事件的写入点必须明确收敛到一个位置。

### 聚合根方法：`domain/diagnosis/case.py` 第 119-121 行

```python
def start_investigation(self, *, at=None) -> None:
    self._transition_to(DiagnosisStatus.INVESTIGATING, at=at)
```

只有一行——委托给 `_transition_to()` 做校验 + 状态更新 + version 自增 + 时间戳更新。

## [4] Strategy Router 选择策略

源码位置：`application/diagnoses.py` 第 237-241 行

```python
strategy = (
    self._strategy_router.select(diagnosis)
    if self._strategy_router is not None
    else self._strategy
)
```

### 解读

- `_strategy_router` 是可选依赖。如果注入了一个 Router 实例，就根据 `diagnosis.problem_type` 动态选择 Strategy（如 `application_error_v1`）；否则使用构造函数里注入的默认 `_strategy`。
- 为什么是可选依赖？——Phase 0 时只有一个策略，Router 是多余的。Phase 2 引入多个策略后才加 Router。但为了不破坏旧代码，Router 设为 optional，没注入就退化到默认策略。
- 这个步骤只读 `DiagnosisCase`，不修改任何状态。

## [5] ToolResourceResolver 解析资源

源码位置：`application/diagnoses.py` 第 242-246 行

```python
resources = (
    await self._tool_resource_resolver(diagnosis)
    if self._tool_resource_resolver is not None
    else ToolResourceContext()
)
```

### 解读

- `_tool_resource_resolver` 根据 `DiagnosisCase.service_id` 去查 `ServiceProfile` → 获取该服务的源码路径、日志目录、配置路径、健康检查 URL。
- 当装配了项目当前的服务资源解析器时，未关联服务或服务记录不存在会回退到 Settings 构造的全局默认资源；只有完全没有注入 Resolver 时，`run()` 才创建空的 `ToolResourceContext()`。服务记录缺失仍回退默认资源是当前兼容性取舍，也可能成为后续需要收紧的安全边界。
- 同样是可选依赖的设计——没有 Resolver 时优雅降级，不阻塞核心流程。

## [6] ToolLoopRunner.run()

源码位置：`application/diagnoses.py` 第 249-269 行

```python
result = await self._runner.run(
    diagnosis=diagnosis,
    strategy=strategy,
    context=ToolLoopContext(
        actor=actor,
        environment=environment,
        audit_correlation_id=correlation_id,
        permissions=frozenset({"knowledge:read", "code:read", "config:read", "log:read", "health:read"}),
        max_tool_output_bytes=max_tool_output_bytes,
        resources=resources,
    ),
    budget=self._budget,
)
```

### 解读：三个关键信息

#### 6.1 权限白名单（第 256-264 行）

五个只读权限塞进 `frozenset`（不可变集合）：`knowledge:read`、`code:read`、`config:read`、`log:read`、`health:read`。全部是 read 操作——Runner 不能写代码、不能改配置、不能执行命令。

#### 6.2 Runner 不直接操作 SQLAlchemy Repository（第 247-248 行注释）

Runner 除了接收 `diagnosis`、`strategy`、`context` 和 `budget`，构造时还注入了 ExecutionRepository、EvidenceStore、PlanRepository 等 Port。它会通过这些稳定契约持久化 AgentRun、ToolRun、Plan 和 Evidence，但不在 Runtime 中直接创建 SQLAlchemy Session 或具体 Repository Adapter。

#### 6.3 预算约束

`self._budget` 在 `ApplicationService` 构造时注入，包含轮次上限、工具调用次数上限、总时间上限、输出字节数上限。Runner 不知道这些值从哪来。

## [7] _apply_result(diagnosis_id, result)

源码位置：`application/diagnoses.py` 第 345-371 行

```python
async def _apply_result(self, diagnosis_id, result):
    async with self._sessions.begin() as session:
        diagnosis = await repository.get(diagnosis_id)
        if diagnosis.status is DiagnosisStatus.CANCELLED:
            return  # ← 已取消的不再写状态
        expected_version = diagnosis.version
        if result.termination_reason is AgentTerminationReason.COMPLETED and result.conclusion is not None:
            diagnosis.record_initial_conclusion(
                conclusion, needs_input=bool(result.conclusion.missing_information)
            )
        else:
            diagnosis.mark_inconclusive()
        await repository.save(diagnosis, expected_version=expected_version)
```

### 解读：四个关键判断

#### 7.1 CANCELLED 守卫（第 357-358 行）

如果在 Runner 运行期间用户调了 `cancel()`，`_mark_cancelled()` 已经把状态写成 `CANCELLED`。此时 `_apply_result` 直接 return，不覆盖取消状态。这是并发场景下的防御逻辑——AgentRun 的完成回调和用户取消回调之间存在竞态。

#### 7.2 只有 COMPLETED + 有结论才推进到等待确认（第 360-368 行）

终止原因必须是 `COMPLETED` 且 `conclusion is not None` 双条件成立，才调用 `record_initial_conclusion()`。注意 `missing_information` 字段的存在——如果结论里标注了"缺少关键信息"，就进 `WAITING_FOR_INPUT` 而非 `WAITING_FOR_CONFIRMATION`。

#### 7.3 其他所有终止原因 → INCONCLUSIVE（第 369-370 行）

`max_turns_exceeded`、`time_budget_exceeded`、`model_error`……不管什么原因，只要不是 `COMPLETED`，统一进 `INCONCLUSIVE`。这是一种保守的降级策略——宁可少给结论，也不给不可靠的结论。

#### 7.4 聚合根的 `record_initial_conclusion()`

`domain/diagnosis/case.py` 第 151-171 行：

```python
def record_initial_conclusion(self, conclusion, *, needs_input):
    target = WAITING_FOR_INPUT if needs_input else WAITING_FOR_CONFIRMATION
    self._transition_to(target, at=at)
    self.conclusion = dict(conclusion)
```

根据 `needs_input` 自动分流，结论写入 `self.conclusion` 字段。注意命名为 `record_initial_conclusion` —— "initial" 意味着这是模型的初始结论，后续人工可能通过 Confirmation 追加或修正。

## [8] Repository.save(DiagnosisCase, expected_version)

源码位置：`adapters/persistence/diagnosis_repository.py` 第 62-83 行

```python
async def save(self, diagnosis: DiagnosisCase, *, expected_version: int) -> None:
    statement = (
        update(DiagnosisRecord)
        .where(
            DiagnosisRecord.id == str(diagnosis.id),
            DiagnosisRecord.version == expected_version,    # ← 乐观锁条件
        )
        .values(
            title=diagnosis.title,
            service_id=..., problem_type=..., status=...,
            version=diagnosis.version,                     # ← 写入新版本号
            updated_at=diagnosis.updated_at,
            conclusion_json=diagnosis.conclusion,
        )
    )
    result = await self._session.execute(statement)
    if result.rowcount != 1:
        raise ConcurrentDiagnosisUpdate(diagnosis.id, expected_version)
```

### 解读

- WHERE 条件是 `version == expected_version`，也就是"[2] 或 [7] 步骤中读到的那一版"。如果在此期间有其他进程改过这条记录，`version` 已经自增了，WHERE 匹配不上，`rowcount=0`，抛异常。
- VALUES 中写的是 `diagnosis.version`（新值），和 `expected_version` 比已经 +1 了。
- 为什么不在 Repository 内部自己算 version？——因为 version 只由 `DiagnosisCase._transition_to()` 自增，Repository 只是"验证我写的是不是基于最新的"，不自己决策版本号。这是领域层和持久化层职责分离的体现。
