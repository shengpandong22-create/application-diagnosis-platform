# 第0课：领域名词术语表

> 学习其他课时遇到陌生名词时，来这里速查。每个名词的解释都基于项目源码，不引入外部概念。

---

## 一、领域对象（核心业务实体）

### DiagnosisCase（诊断用例 / 工单）

代表一次完整的故障诊断案件。一个 DiagnosisCase 对应一个"工单"——用户提交症状和日志后创建，经历 CREATED → INVESTIGATING → WAITING_FOR_* → CONFIRMED/REJECTED/INCONCLUSIVE/CANCELLED 的状态流转。它是整个诊断的聚合根，内部维护了状态转移规则、乐观锁版本号，任何状态变更都必须经过它。

### AgentRun（调查运行 / 出勤记录）

代表一次 Agent 调查的执行。一个 DiagnosisCase 可以包含多次 AgentRun——比如系统初步调查后缺信息等用户补充，补充完后重新启动调查。每次 AgentRun 独立记录自己为什么开始、怎么结束、消耗了多少 Token、调了哪些工具。

### ToolRun（工具调用 / 操作日志）

代表一次具体的工具调用。一次 AgentRun 可以包含多个 ToolRun——因为 LLM 在调查过程中可能跑多轮，每轮可能调多个工具（如先查日志、再读配置、最后读源码）。每个 ToolRun 记录调了哪个工具、参数是什么、成功还是失败、产生了哪些 Evidence。

### Evidence（证据）

代表诊断过程中产生的、可供 LLM 引用以支撑结论的**事实性数据**。Evidence 的来源包括用户输入（症状描述、提交的日志）、工具执行结果（读到的源码内容、配置项、健康检查结果）。每条 Evidence 有独立 UUID 作为正式引用标识、可靠性等级（HIGH/MEDIUM/LOW）、内容的 SHA-256 hash（content_hash），用于防重复，以及脱敏状态。Evidence 是 immutable 的——一旦落库就不再修改。

### Evidence ID（证据引用标识符）

Evidence 持久化到数据库时由系统生成的 UUID。它是整个引用机制的基石——LLM 输出结论时必须引用这些正式 ID，CitationPolicy 只认数据库中存在的真实 ID，不认 LLM 自己编造的字符串。ID 在设计上是不可预测的：LLM 无法猜到下一条 Evidence 会生成什么 ID，因此无法预编合法引用。

### EvidenceDraft / EvidenceCandidate（证据草稿 / 证据候选）

工具执行后产生的、尚未持久化为正式 Evidence 的临时数据。Draft 包含脱敏后的内容、来源类型、可靠性标注，但还没有 UUID——正式 ID 要在落库时才生成。这一层隔离保证 LLM 永远不知道"下一个 Evidence ID 是什么"。

### Confirmation（人工确认）

代表用户对模型结论的最终判断。Confirmation 是一个独立的领域对象，记录谁（actor）、做了什么判断（confirm/reject/continue）、什么时候、附带什么评语。关键设计：Confirmation 是追加记录，不覆盖 DiagnosisCase.conclusion 中保存的模型原始结论——保留"模型说了什么"和"人怎么判的"两条独立的审计线。

### Incident（事件 / 故障事件）

代表经过指纹聚合后的事实例。来自多条同类异常的日志经 `ErrorFingerprint` 聚合后形成 Incident，包含异常类型、采样消息、发生次数（occurrence_count）、首次发现时间、最近一次发现时间、以及可选关联的 DiagnosisCase。Incident 是主动发现链路中的核心领域对象。

### ErrorFingerprint（错误指纹）

将日志事件（异常类型 + 业务栈帧）通过确定性的算法生成的稳定字符串标识。去掉了行号、数字、UUID 等易变信息，只保留 `class#method` 的归一化形式。同一个异常的多次发生（即使行号不同）会生成同一个指纹，从而被聚合到同一个 Incident。

### LogEvent（日志事件）

日志采集层传递到领域层的事件对象。包含服务 ID、环境、异常类型、异常消息、业务栈帧、发生时间等字段。LogEvent 经过 `build_error_fingerprint()` 转换为 ErrorFingerprint，再通过 Incident 聚合。

### ServiceProfile（服务档案）

描述被诊断服务的静态信息：服务名、源码路径、日志目录、配置路径、健康检查 URL。在 ToolResourceResolver 解析诊断资源时被查询，用于为特定服务构造受限的 Adapter 实例（如只允许读取该服务的源码目录）。

### DiagnosisPlan（诊断计划）

一次 AgentRun 开始时由规则生成的解释性文本，持久化为 Plan 对象。内容包括：使用哪个 Strategy、允许哪些工具、预计关注什么问题方向。Plan 不控制工具执行顺序，纯粹给用户看"本次诊断准备怎么查"。它不是 Plan-and-Execute 中的执行计划。

### AuditEvent（审计事件）

记录系统发生的关键操作：谁在什么时候对什么对象做了什么。包括：诊断创建、调查启动、证据创建、用户补充信息、人工确认/驳回等事件。审计事件是诊断全链路的可追溯性基石。

## 二、运行时组件

### ToolLoopRunner（Agent 循环运行时）

整个系统中最核心的执行引擎。负责管理 LLM 多轮对话、工具调用、预算控制、Evidence 持久化、引用校验。Runner 接收 DiagnosisCase、Strategy、ToolLoopContext 和 Budget 作为输入，输出 ToolLoopResult。它不直接修改 DiagnosisCase 的状态——状态推后由 ApplicationService 完成。

### ToolLoopResult（工具循环结果）

Runner 返回给 ApplicationService 的"运行摘要"。包含终止原因（termination_reason）、候选结论（可选）、产生的 Evidence ID 列表、以及错误信息（如果失败）。ApplicationService 根据 termination_reason 和 conclusion 字段决定下一步推进到哪个状态。

### DiagnosisConclusion（诊断结论）

LLM 输出的结构化 JSON 结论，包含症状摘要、事实列表（每个事实引用 Evidence ID）、根因列表、修复建议、缺失信息。它是 LLM 的直接产出物，在被 CitationPolicy 校验之前只是候选。

### ToolLoopContext（工具循环上下文）

Runner 需要的运行环境参数集合：actor（调用者）、environment（环境名）、audit_correlation_id（审计追踪 ID）、permissions（权限白名单）、max_tool_output_bytes（工具输出上限）、resources（ToolResourceContext）。

### ToolExecutionContext（工具执行上下文）

单个工具调用所需的运行参数：当前诊断ID、AgentRun ID、actor、deadline（超时绝对时间）、权限、ProblemType、输出字节上限、以及各个 Adapter 实例（code_repository、log_reader 等）。

### ToolResourceContext（工具资源上下文）

描述本次诊断可用的工具资源绑定：code_repository、log_reader、config_repository、health_check_client 的具体实例，以及 available_tool_names（真正可调用的工具名称）。由 ToolResourceResolver 根据 ServiceProfile 构造。

## 三、策略与路由

### DiagnosisStrategy（诊断策略）

定义了针对特定故障类型的 Prompt 模板、允许使用的工具白名单、以及输出格式要求。不同策略对应不同故障场景——例如 ApplicationErrorStrategy 允许源码和健康检查工具，NetworkStrategy 排除了源码工具。

### StrategyRouter（策略路由器）

根据 DiagnosisCase 的 title、symptom、submitted_log 内容，用正则关键词匹配的方式选择最合适的 Strategy。唯一高分者当选，平票或零票走 fallback。使用纯规则而非 LLM 做路由——便宜、稳定、可测试。

---

## 四、闸门与策略（校验机制）

### DiagnosticToolRegistry（工具注册表）

管理所有可用诊断工具的注册、启用状态、白名单校验和权限检查。核心方法 `resolve()` 执行五层闸门校验：注册存在 → enabled → Strategy 白名单 → ProblemType 匹配 → 权限检查。同时负责生成发给 LLM 的工具定义（Function Calling 格式）。

### CitationPolicy（引用校验策略）

在模型输出结论后、结论被接受前执行的校验规则。检查三个维度：引用的 Evidence ID 是否真实存在、是否归属于当前 Diagnosis、引用的可靠性等级是否足够支撑结论的置信度。纯知识引用不能单独支撑 probable 级别结论。

### DiagnosisTriggerPolicy（诊断触发策略）

主动发现链路中的触发决策规则。当前实现是：同一 Incident 只能关联一个 Diagnosis——如果已经关联过（`diagnosis_id is not None`），不管该 Diagnosis 处于什么状态，都不再自动触发新的诊断。

## 五、适配器与基础设施

### Redactor（脱敏器）

在用户输入进入持久化和 LLM 上下文之前，执行基于正则的敏感信息过滤。匹配 API Key、Token、密码、数据库连接串等模式，替换为 REDACTED 标记。脱敏是不可逆的，且必须在持久化之前完成。

### Ports（端口/接口）

六边形架构中的抽象接口层，定义业务逻辑需要的契约。例如 CodeRepository、LogReader、EvidenceStore、LLMClient、NotificationClient 等。领域层只依赖 Ports，不依赖任何具体的 Adapter 实现。

### Adapters（适配器）

Ports 接口的具体实现层。例如 LocalCodeRepository（实现 CodeRepository，读本地文件）、SqlAlchemyEvidenceStore（实现 EvidenceStore，写数据库）、RabbitMQLogEventConsumer（实现消息消费）。更换外部依赖只需实现对应的 Port 接口。

### Bootstrap（依赖装配容器）

负责把 Settings、数据库连接、LLM Client、工具、Strategy、ApplicationService 等所有组件显式装配在一起的工厂函数集合。不包含业务逻辑，只做"接线"工作。本质是手工实现的依赖注入（IoC）。

## 六、领域枚举

### DiagnosisStatus（诊断状态）

DiagnosisCase 的八种状态：`CREATED`（新建）→ `INVESTIGATING`（调查中）→ `WAITING_FOR_INPUT`（等待补充信息）/ `WAITING_FOR_CONFIRMATION`（等待人工确认）→ `CONFIRMED`（已确认）/ `REJECTED`（已驳回）/ `INCONCLUSIVE`（证据不足）/ `CANCELLED`（已取消）。后四种是终态。

### AgentTerminationReason（Agent 终止原因）

AgentRun 结束的原因：`COMPLETED`（正常完成，有结论）、`MAX_TURNS_EXCEEDED`（轮次用完）、`TIME_BUDGET_EXHAUSTED`（总时间超时）、`TOOL_BUDGET_EXHAUSTED`（工具次数用完）、`MODEL_ERROR`（LLM 调用失败）、`CANCELLED`（用户取消）、`INTERNAL_ERROR`（内部异常）、`INCONCLUSIVE`（证据不足无法结论）。

### ProblemType（问题类型）

诊断的问题分类：`GENERIC_APPLICATION_ERROR`（通用应用错误）、相关的网络/配置问题类型等。用于 Strategy 路由和工具适配。

### EvidenceType（证据类型）

Evidence 的分类：`USER_STATEMENT`（用户口述）、`LOG_EXCERPT`（日志片段）、`CODE_EXCERPT`（代码片段）、`HEALTH_REPORT`（健康检查报告）、`CONFIG_SNAPSHOT`（配置快照）、`KNOWLEDGE_ENTRY`（知识条目）。

### EvidenceReliability（证据可靠性）

Evidence 的可信度等级：`HIGH`（机器产生的事实，如日志、源码）、`MEDIUM`（用户口述的描述）、`LOW`（推测性信息）。

## 七、架构概念

### 聚合根（Aggregate Root）

DDD 概念。DiagnosisCase 是诊断聚合的聚合根——所有对诊断状态和结论的修改都必须通过它的方法（如 `record_initial_conclusion()`、`confirm()`），不能直接改字段。聚合根内部维护了状态转移规则和乐观锁版本号。

### ApplicationService（应用服务）

位于 API 层和领域层之间的用例编排层。负责：从 Repository 加载聚合根 → 调用聚合根方法推动状态 → 保存回 Repository。DiagnosisApplicationService.run() 是整个诊断主链路的入口。

### 渐进式持久化

AgentRun 不是"全部完成后再写数据库"，而是每步操作后立即持久化——创建 AgentRun 时写、每次 LLM 响应后更新、每次工具调用后写 ToolRun + Evidence。失败时已发生的事仍然可追溯。

---

## 八、一段话串联

用户通过 API 创建一个 `DiagnosisCase`（状态为 `CREATED`），提交原始日志和症状——这些信息先经过 `Redactor` 脱敏，生成 `EvidenceDraft`，然后持久化为带正式 `Evidence ID` 的 `Evidence` 对象。用户点击"启动诊断"，`DiagnosisApplicationService` 将 `DiagnosisCase` 推进到 `INVESTIGATING`，通过 `StrategyRouter` 选择匹配的 `DiagnosisStrategy`，通过 `ToolResourceResolver` 根据 `ServiceProfile` 构造 `ToolResourceContext`，然后把这一切交给 `ToolLoopRunner`。Runner 在 `ToolLoopContext` 和 `AgentBudget` 约束下进入多轮循环——每轮把诊断上下文、Strategy 提示词、`Evidence Catalog` 打包发给 LLM，LLM 提议工具调用或输出 `DiagnosisConclusion`。工具调用经过 `DiagnosticToolRegistry` 五层闸门校验后执行，结果生成新的 `EvidenceCandidate`，经 hash 去重后持久化为正式 `Evidence`，每个工具调用记录为 `ToolRun`。LLM 给结论时，`CitationPolicy` 校验引用的 `Evidence ID` 是否真实且归属于当前诊断——格式错误和引用错误各有有限次修正机会。全部校验通过后返回 `ToolLoopResult`，`DiagnosisApplicationService._apply_result()` 根据终止原因调用 `DiagnosisCase` 的对应方法推进到 `WAITING_FOR_CONFIRMATION` 或 `INCONCLUSIVE`。最终用户通过 `Confirmation` 追加确认、驳回或要求继续调查，`AuditEvent` 全程记录操作轨迹。
