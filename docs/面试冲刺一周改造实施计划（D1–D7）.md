### 主线

| 主线                   | 对应弱点                                                     | 完成标志                                    |

## 2. D1：时间注入收口（结构日）

### 已确认的代码事实（改前先核对，行号可能漂移，以搜索为准）

1. **注入先例已存在**：`src/app_diagnosis/agent/runtime/tool_loop.py` 约 59-60 行，
   `ToolLoopRunner.__init__` 已有 `clock: Callable[[], datetime] = lambda: datetime.now(UTC)` 参数——照抄这个模式即可，不是发明新东西。
2. **domain 层已支持**：`src/app_diagnosis/domain/diagnosis/case.py` 的 `DiagnosisCase.create(*, now: datetime | None = None)`；
   `domain/evidence/models.py` 的 `Evidence.create(*, now=None)` 同样支持。
3. **断链点（时间炸弹根因）**：
   - `src/app_diagnosis/application/evidence_diagnoses.py` 约 71 行：`DiagnosisCase.create(...)` 未传 `now`
   - `src/app_diagnosis/application/diagnoses.py` 约 185 行：同上
   - `src/app_diagnosis/adapters/persistence/evidence_store.py` 约 30 行：`base_time = datetime.now(UTC)` 直连
4. **失败断言链**：`tests/integration/test_phase4d_operations.py:28`（`waiting_for_confirmation`）→
   `src/app_diagnosis/application/daily_summaries.py` 约 48-52 行按 `day` 过滤 `diagnoses.created_at` →
   fixture `tests/integration/test_active_discovery_api.py` 的 `_event()` 中 `occurred_at` 写死 `datetime(2026, 8, 8)`。

### 步骤

1. `EvidenceAwareDiagnosisApplicationService` 与 `DiagnosisApplicationService` 的 `__init__` 增加
   `clock: Callable[[], datetime] = lambda: datetime.now(UTC)`（与 tool_loop 同款默认值），`create` 时传入
   `DiagnosisCase.create(now=self._clock())`、`Evidence.create(now=...)`。
2. `evidence_store.py` 的 `base_time` 改为可注入（构造参数，默认真实时钟）。
3. 测试 fixture（`tests/integration/test_service_catalog_api.py` 的 `migrated_client`）暴露 clock 注入口，
   `test_phase4d_operations.py` 注入**固定时钟**（如 `datetime(2026, 8, 8, 12, 0, tzinfo=UTC)`），
   保持 `day=2026-08-08` 断言不变——测试从此与执行日期解耦。
4. 新增跨日期回归测试：同一 fixture，用两个不同注入日期（如 2026-01-01 与 2026-12-31）各跑一遍
   daily-summary，断言计数一致。**这一条是防线，防未来再出时间耦合。**
5. 跑 `uv run pytest`，目标 247 项全绿。
6. 写 `docs/05-decisions/0005-time-as-injectable-dependency.md`（ADR）：
   背景（时间炸弹根因链）→ 决策（时间走 Callable 注入，遵循既有 tool_loop 模式）→
   备选（只改 fixture 动态日期，为何不选：治标）→ 影响（测试可注入固定时钟，跨日期回归成为标准防线）。
7. 更新 `docs/README.md` ADR 章节链接。

### 验收标准

- `uv run pytest` 全绿，且把系统日期想象成任意一天都不会挂（跨日期回归测试证明）。
- ADR-0005 落盘，`docs/README.md` 有链接。

## 3. D2：评测集扩容（数据日·上）

### 已确认的代码事实（执行前已校正）

1. `evals/cases/phase4a-java-lab-cases.json` 是 8 条 **Java Lab 故障定义**，不是 `EvaluationCase`，不能直接交给评分 CLI。
2. `evals/cases/phase4a-quality-baseline.json` 才是带 `observation` 的可评分案例。评测 CLI：`uv run python -m app_diagnosis.evaluation.cli --cases <json> --output <json>`，
   指标体系已内置（无需开发）：root_cause top1/top3 命中率、citation precision/recall、
   unsupported_claim_rate、high_confidence_error_rate、tool_selection_accuracy、latency、tokens、cost、类目混淆矩阵。
3. `tests/unit/evaluation/test_phase4a_java_lab_cases.py` 断言 `len(cases) == 8` 且校验 dataset_version——
   **所以不要修改这个 8 用例文件**。

### 步骤

1. 建立三层契约：`EvaluationScenario`（输入与真值）→ `EvaluationObservation`（真实运行事实）→ `EvaluationCase`（评分输入）。禁止用手写 observation 冒充模型结果。
2. 新建 `evals/cases/real-model-v1-definitions.json`，首批 12 条：覆盖 Java Lab 已有 8 类故障，并增加 4 条用户描述鲁棒性变体；暂不虚构 Java Lab 无法触发的新故障。
3. 标注规范直接放入版本化数据集：
   - top1 命中 = 结论的**第一个** root_cause 语句包含任一 allowed 关键词
   - top3 命中 = 前三个 root_cause 拼接后包含任一 allowed 关键词
   - 关键词选"技术事实词"（类名、异常语义），不选"套话词"（错误、失败）
4. pytest 只验证场景 Schema、唯一 ID、类别覆盖和定义中不含 observation；模型 Observation 必须由 D3 脚本产生。

### 验收标准

- 12 条场景可由 `EvaluationScenarioDataset` 严格解析，8 个基础故障均被覆盖。
- 场景定义不包含伪造 observation；新增确定性测试通过；原有测试不回退。

## 4. D3：真实模型 v1 全量跑（数据日·下）

### 已确认的代码事实

- `scripts/diagnose-java-log-real.py`（约 9.6KB）已实现"单条真实模型诊断"链路：读 .env 配置 → 创建诊断 → run → 落结果。**批量评测脚本参照它写。**

### 步骤

1. 新写 `scripts/eval-real-model.py`（参照 `diagnose-java-log-real.py` 的容器装配与 run 流程）：
   - 逐用例：以 case 的 symptom/log 文本创建诊断 → 启动 run → 等待终态
   - 导出每个用例的 `observation`（字段对齐 `evaluation/models.py`：conclusion、evidence、
     tool_names、tool_statuses、termination_reason、observed_category、confidence、latency_ms、tokens、cost）
   - 汇总成 `evals/results/real-model-v1-observations.json`
   - 失败用例（LLM 异常、超时）单独记录为 `termination_reason: error_*`，不中断整轮
2. 跑之前确认 `.env` 指向成本可控的模型（DeepSeek 等），记录模型名、温度、prompt_version（记 `real-v1`）。
3. 执行：`uv run python scripts/eval-real-model.py --cases evals/cases/real-model-v1-cases.json --output evals/results/real-model-v1.json`
4. 评分：`uv run python -m app_diagnosis.evaluation.cli --cases <含observation的cases> --output evals/results/real-model-v1-suite.json`
5. 写 `docs/04-validation/2026-XX-XX-真实模型v1基线评测.md`：环境（模型/温度/版本）、全量指标表、
   逐用例通过明细。
6. 失败分析初稿（D4 的输入）：对每个失败用例记录 3 行——失败码（category_mismatch / root_cause_mismatch /
   invalid_evidence_citations / ...）、模型实际说了什么（root_cause 原文摘录）、初判归因（提示词歧义 / 证据不足 / 路由错 / 结构化失败 / 标注过严）。

### 验收标准

- 一份 v1 基线报告 + 一份失败分析初稿落盘。数字即使难看也要真实（难看的真数字远好于没有数字）。

## 5. D4–D5：评测迭代闭环（数据日·核心）

### 原则

- **每轮只动一个变量**（提示词措辞 / 策略路由关键词 / 工具返回摘要格式），prompt_version 递增（real-v2、real-v3）。
- 迭代对象只选失败分析中**出现 ≥2 次的失败模式**（单次出现的多半是随机性，不值得改）。

### 步骤

1. 从失败分析初稿聚类 top 2-3 失败模式。
2. 针对每个模式做最小改动，跑 v2（同 D3 流程），产出对比表：

   | 指标                         | v1   | v2   | v3   |
   | ---------------------------- | ---- | ---- | ---- |
   | root_cause_top1_rate         |      |      |      |
   | root_cause_top3_rate         |      |      |      |
   | citation_precision / recall  |      |      |      |
   | unsupported_claim_rate       |      |      |      |
   | high_confidence_error_rate   |      |      |      |
   | 平均 latency / tokens / cost |      |      |      |

3. 若 v2 无提升或回退：回滚改动，把"尝试了什么、为什么没效"记进失败分析——**负结果也是面试证据**。
4. 终版写 `docs/04-validation/2026-XX-XX-真实模型迭代评测报告.md`：对比表 + 每轮改动说明 + 失败模式分析（终稿）。

### 验收标准

- ≥2 个评测版本的真实对比数据。
- 失败模式分析能回答"哪个失败模式被什么改动修复了多少"。
